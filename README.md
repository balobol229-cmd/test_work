# CheckStock: где сейчас товар

Веб-прототип для менеджера маркетплейса. По каждому артикулу видно, сколько лежит на каждом складе фулфилмента (ФФ), сколько свободно, сколько в резерве FBS, что едет между складами, что ушло на склад WB по FBO и что отправлено клиенту.

Стек: Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2.0, Alembic, Jinja2. Интерфейс рендерит сервер, сборки фронтенда нет.

## Запуск

### Через Docker (рекомендуется)

Нужен только Docker.

```bash
docker compose up --build
```

Откройте http://localhost:8000. При старте накатываются миграции и загружаются тестовые данные из задания: один магазин, ФФ «Север» и «Юг», SKU-101, SKU-102, SKU-103.

Тесты в контейнере, на том же PostgreSQL:

```bash
docker compose run --rm app pytest
```

Вернуть данные к тестовым: кнопка «Сбросить к тестовым данным» внизу меню или `make reset`.

### Локально

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/) и PostgreSQL на `localhost:5432`.

```bash
make dev        # создаёт базу checkstock, миграции, тестовые данные, сервер с автоперезагрузкой
make dev-test   # тесты; база checkstock_test создаётся сама
```

Другая база задаётся переменной `DATABASE_URL`, например `postgresql+psycopg://user:pass@host:5432/checkstock`.

## Как проверить руками

Каждый сценарий начинайте после сброса данных.

1. **Резерв FBS.** Заказ FBS: SKU-101 с Севера, 3 шт. На Севере станет физически 10, резерв 3, доступно 7. «Отправить клиенту»: физически 7, «К клиенту» 3.
2. **Перемещение.** SKU-101 с Севера на Юг, 4 шт. На Севере 6, в колонке «Между ФФ» 4, на Юге пока 6, итог по товару по-прежнему 16. «Принять»: на Юге 10.
3. **FBO.** SKU-103 с Юга, 2 шт. На Юге 2, «FBO в пути» 2. «Принята складом WB»: «Склад WB» 2.
4. **Нехватка при достаточном общем остатке.** Заказ FBS: SKU-101 с Севера, 12 шт. На Севере 10, всего 16. Заказ сохраняется со статусом «ждёт товара» и предлагает «Разделить: 10 с Севера + 2 с Юга» или «Довезти 2 шт. с Юга». Для SKU-103 с Севера предлагается «Взять все с Юга». Поставка FBO при нехватке отклоняется с теми же вариантами, остатки не меняются.
5. **Удаление ФФ с остатком.** Удалите Юг. Склад пропадает из списков для новых операций, но его остаток виден на экране остатков как «Юг · удалён», история на месте, вывезти товар можно перемещением. Если на складе есть резерв, к нему едет перемещение или заказ ждёт товара, удаление запрещено с объяснением.
6. **Повтор.** В Swagger дважды отправьте `POST /api/fbs` с одним заголовком `Idempotency-Key`: второй ответ вернёт тот же документ и `"replayed": true`. Дважды `POST /api/fbs/{id}/ship`: второй раз остаток не уменьшится. В интерфейсе: отправьте форму, нажмите «Назад» и отправьте снова — будет сообщение «Повтор: операция уже проведена».

После каждого шага штамп сверки в шапке должен оставаться зелёным.

## Ключевые решения

### Учёт через документы и журнал, а не правку чисел

Остатки никогда не правятся напрямую. Каждое действие — это документ (приход, перемещение, заказ FBS, поставка FBO) со статусом, и каждое изменение статуса пишет строку в журнал движений: «откуда → куда, сколько».

Места, между которыми двигается товар: поставщик, ФФ (свободно), ФФ (резерв), в пути между ФФ, в пути на склад WB, склад WB, клиент. Единица не может появиться или исчезнуть, она только переходит из одного места в другое. Поэтому «остатки сходятся после каждого действия» проверяется, а не принимается на веру.

| Документ | Переходы | Движение |
| --- | --- | --- |
| Приход | проведён | поставщик → ФФ |
| Перемещение | в пути → принято | ФФ-отправитель → в пути → ФФ-получатель |
| Заказ FBS | ждёт товара → в резерве → отправлен / отменён | ФФ → резерв ФФ → клиент (или обратно в ФФ) |
| Поставка FBO | в пути → принята | ФФ → в пути на WB → склад WB |

### Три источника и сверка

Данные лежат в трёх местах, и они независимо подтверждают друг друга:

- `stock` — текущий остаток на ФФ: физически и в резерве. Это материализованная сумма журнала: её удобно блокировать, а CHECK-ограничения базы не дают остатку и резерву уйти в минус, а резерву превысить физический остаток;
- `movements` — журнал, только добавление;
- `documents` — что сейчас в пути, в резерве, у WB, у клиента.

Сверка ([app/core/views.py](app/core/views.py), `reconcile`) проверяет: остатки равны балансу журнала по каждому складу; товар в пути, у WB и у клиента по документам равен журналу; каждая принятая единица числится ровно в одном месте. В тестах сверка вызывается после каждого шага сценария.

### Параллельные операции

Каждая операция — одна транзакция. Перед изменением она блокирует строки `stock` этого товара (`SELECT … FOR UPDATE`) в порядке `warehouse_id`. Два менеджера, одновременно резервирующие последние единицы, выстраиваются в очередь: один получает резерв, второй — «ждёт товара». Порядок блокировок одинаковый, поэтому дедлоков нет. Склад читается с `FOR SHARE`, а удаление склада берёт `FOR UPDATE`, так что склад не удалят посреди операции на нём. Это проверено тестами с потоками на настоящем PostgreSQL.

### Повторное подтверждение

- Переходы статуса идемпотентны: если заказ уже отправлен, повторное «Отправить» ничего не меняет и возвращает `replayed`. Документ блокируется `FOR UPDATE`, поэтому даже четыре одновременных подтверждения списывают товар один раз.
- Создание документа принимает ключ повтора: `Idempotency-Key` в API, скрытое поле в каждой форме. Двойной клик или повторная отправка формы возвращают уже созданный документ. Одновременные запросы с одним ключом встают в очередь на `pg_advisory_xact_lock`.

### Нехватка на выбранном ФФ

Для FBS заказ не отклоняется. Он сохраняется со статусом «ждёт товара», спрос виден на экране остатков, а менеджер выбирает: взять всё с другого ФФ, разделить заказ между складами (все части резервируются в одной транзакции) или довезти недостающее перемещением. Это тот же принцип, что в ТЗ Ракеты: нехватка не превращает спрос в ноль.

FBO-поставку собирают с одного склада, поэтому при нехватке она отклоняется, и интерфейс сразу предлагает отгрузить с другого ФФ или довезти товар.

### Удаление склада

Удаление мягкое: у склада ставится `archived_at`. Его остаток и история не трогаются и видны на экране остатков с пометкой «удалён». Принимать товар и отгружать заказы с такого склада нельзя, вывезти остаток перемещением можно. Если у склада есть незавершённые операции (резерв, входящее перемещение, ждущий заказ), удаление запрещено, и сообщение говорит, что мешает. Имя удалённого склада можно снова использовать.

### «Удалить» операцию — это отмена, а не стирание

Кнопка «Удалить» у заказа, перемещения, поставки или ошибочного прихода проводит обратное движение. В истории остаются обе записи, сверка сходится. Удалить можно, пока операция не завершена: принятое перемещение отменяется только обратным перемещением, а приход — только пока весь он ещё свободен на складе.

### Магазины не смешиваются

Товар принадлежит магазину (`stores`), артикул уникален внутри магазина, у магазина есть поле площадки. В задании один магазин WB, но схема готова к нескольким кабинетам и к Ozon и Яндекс Маркету без переделки учёта.

## Структура

Слои повторяют схему «Архитектура и поток данных» из ТЗ Ракеты: источники → единая база → расчётное ядро → веб-интерфейс.

```
app/
  sources/seed.py      источник данных: тестовые данные задания
  db/models.py         единая база: магазины, товары, склады, остатки, документы, журнал
  core/inventory.py    расчётное ядро: все операции, которые меняют остатки
  core/views.py        чтение: экран остатков, операции, история, сверка
  web/api.py           JSON API
  web/pages.py         HTML-страницы и формы
  templates/, static/  интерфейс
migrations/            Alembic
tests/                 51 тест на PostgreSQL
```

## Тесты

Тесты идут на настоящем PostgreSQL: учёт держится на транзакциях, блокировках и CHECK-ограничениях, и мок базы проверил бы не то. Схема накатывается теми же миграциями Alembic, перед каждым тестом данные заводятся заново.

| Файл | Что проверяет |
| --- | --- |
| `test_accounting.py` | приход, резерв, перемещение, отправка, приёмка, FBO; сквозной сценарий со сверкой после каждого шага |
| `test_shortage.py` | нехватка на ФФ: ожидание, разделение, перенос на другой ФФ, довоз; нехватка везде; отказ FBO |
| `test_warehouses.py` | добавление, переименование, удаление с остатком; запреты удаления; удалённый склад не участвует в вариантах |
| `test_idempotency.py` | повторы отправки, приёмки, отмены; ключ повтора; одновременные отправки и резервы из нескольких потоков |
| `test_delete.py` | удаление прихода, перемещения, FBO и заказа обратным движением; запреты |
| `test_api.py` | страницы открываются, коды ответов API, повтор формы |

## Как использовался ИИ

Код написан вместе с Claude: модель данных, операции, тесты и вёрстку генерировал ИИ по моим решениям. Сами решения — учёт через журнал движений, мягкое удаление складов, поведение при нехватке, «удалить = отменить» — я принимал и проверял сам.

Проверка результата:
- тесты на складских сценариях из задания, включая одновременные запросы, на настоящем PostgreSQL;
- сверка трёх источников после каждого шага;
- ручной прогон всех сценариев в интерфейсе, по ходу исправлены найденные мелочи: место назначения по умолчанию совпадало с местом отправки, сообщение об ошибке уезжало за пределы экрана.
